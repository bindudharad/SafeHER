## 1. Vulnerability Background & Remediation

The initial audit revealed a critical security vulnerability in the legacy SafeHER application:
> **Audited Flaw:** Evidence records in the SQLite database were marked `is_encrypted = 1`, but the actual uploaded media files were written to disk as plaintext binary streams. Anyone with local file system read access could view sensitive evidence without decryption keys.

### Remediated Architecture:
SafeHER has replaced this flawed mechanism with an industrial-grade **Envelope Cryptography Engine**:
1. Every file written to disk is encrypted with a unique, single-use 256-bit symmetric Data Encryption Key (DEK).
2. The DEK is encrypted (wrapped) using an asymmetric master RSA Key Encryption Key (KEK) via RSA-OAEP.
3. Every file includes Authenticated Associated Data (AAD) binding the ciphertext to the specific `evidence_id` and `user_id`.
4. Plaintext is decrypted strictly in RAM buffers for authenticated users and never persisted unencrypted to storage.

## 2. Cryptographic Specifications

### 2.1 Symmetric Encryption: AES-256-GCM
- **Cipher:** AES (Advanced Encryption Standard) in Galois/Counter Mode (GCM).
- **Key Size:** 256 bits (32 bytes) generated via OS CSPRNG (`os.urandom(32)`).
- **Nonce / IV:** 96 bits (12 bytes) CSPRNG nonce per encryption operation. Nonces are never reused.
- **Authentication Tag:** 128-bit (16 bytes) MAC generated by GHASH.
- **Authenticated Associated Data (AAD):**
  $$\text{AAD} = \text{evidence\_id} \parallel \text{":"} \parallel \text{user\_id} \parallel \text{":v1"}$$
  This cryptographically binds the file to its database record and owning user. If an attacker swaps encrypted files between evidence records or users, decryption immediately throws an authentication error.

### 2.2 Asymmetric Master Key Management: RSA-OAEP
- **Keypair:** RSA 2048-bit (upgradable to 4096-bit) master keys stored in `backend/storage/keys/master-v1_*.pem`.
- **Padding:** Optimal Asymmetric Encryption Padding (OAEP) with MGF1 and SHA-256.
- **File Format:** Encrypted envelope blob stored at `backend/storage/vault/{evidence_id}.enc` containing:
  - Header: Magic bytes (`SAFEHER_ENC_V1`)
  - Key ID: UTF-8 string identifying the master key
  - Nonce: 12-byte initialization vector
  - Wrapped DEK length + Wrapped DEK: RSA-OAEP encrypted symmetric key
  - Ciphertext + Tag: AES-256-GCM encrypted payload with trailing 16-byte tag.

### 2.3 Evidence Signing & Non-Repudiation: RSA-PSS
- **Signature Scheme:** Probabilistic Signature Scheme (PSS) with SHA-256.
- **Purpose:** Produces digital forensic receipts for court submission proving evidence has remained untampered since initial ingest.

## 3. Atomic Pre-Commit Verification & Safe Migration

### Atomic Roundtrip Ingest Verification:
Before any file upload transaction is committed to the database or storage index:
1. File is encrypted into memory buffer.
2. In-memory roundtrip decryption is immediately attempted using the wrapped DEK.
3. If decrypted bytes do not match the input SHA-256 hash byte-for-byte, the transaction is aborted, and the file is deleted.

### Legacy Evidence Migration CLI (`backend/migrate_evidence.py`):
Provides automated migration of existing unencrypted evidence files:
- `--dry-run`: Scans database and storage, inventorying unencrypted files without modifications.
- `--execute`: Iterates through unencrypted records, performs AES-256-GCM encryption, verifies roundtrip decryption, and updates database records atomically.
